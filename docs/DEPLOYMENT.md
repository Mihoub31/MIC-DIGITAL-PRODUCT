# Deployment

## Architecture

One Node service runs both processes:

- Next.js on the public `PORT`;
- the Express API on `127.0.0.1:3002` (`API_PORT`), reachable only inside the
  container.

Next.js rewrites `/api/*` to `API_URL`, so cookies stay on the public origin and
no CORS setup is needed for the dashboard. The database is a managed PostgreSQL
instance (for example Neon) and is not created by the blueprint.

## 1. Database

1. Create a PostgreSQL database (Neon free tier is supported).
2. Copy the **direct** connection string for migrations (`sslmode=require`).
3. Apply the schema from the repository root, after an explicit approval:

   PowerShell:

   ```powershell
   $env:NODE_ENV="production"
   $env:DATABASE_URL="postgresql://...neon.tech/neondb?sslmode=require"
   npm run db:migrate:production
   ```

   Bash:

   ```bash
   NODE_ENV=production DATABASE_URL="postgresql://...neon.tech/neondb?sslmode=require" \
     npm run db:migrate:production
   ```

4. Keep a backup before future migrations (`pg_dump --format=custom`).

The runtime may use the pooled connection string; migrations should use the
direct one. See [DATABASE.md](DATABASE.md).

## 2. Render Blueprint

The repository contains `render.yaml` for a single free web service
(`node scripts/start-all.js`).

Required environment variables:

| Variable | How to set |
| --- | --- |
| `NODE_ENV` | `production` (in the blueprint) |
| `API_URL` | `http://127.0.0.1:3002` (in the blueprint; baked at build time) |
| `API_PORT` | `3002` |
| `DATABASE_URL` | Secret, entered in the dashboard |
| `SESSION_SECRET` | Generated by Render (`generateValue: true`) |
| `APP_ORIGIN` | Public URL, e.g. `https://creatorpilot.onrender.com` |
| `TRUST_PROXY` | `true` |

Optional email variables (add them in the dashboard):

- `SMTP_URL` + `EMAIL_FROM`, or
- `RESEND_API_KEY` + `EMAIL_FROM` (a verified domain is required for real users).

Never put secrets in `render.yaml`.

### Build and start

- Build: `npm ci --include=dev && npm run build`
  `--include=dev` is required because Next.js and TypeScript are dev
  dependencies and the build may run with `NODE_ENV=production`.
- Start: `node scripts/start-all.js`
- Health check: `/login/`

The free plan sleeps after about 15 minutes without traffic and wakes on the
next request. A single service keeps the usage within the free instance hours,
which is why the API is not deployed separately.

## 3. Post-deployment checks

1. `GET /login/` returns 200.
2. Register a test account; the dashboard opens.
3. Create a workspace, invite an existing account and change a role.
4. Request a password reset and confirm the email arrives and the link works.
5. Check the API logs for `email provider: smtp|resend` and no configuration
   errors.

Delete test accounts afterwards.

## 4. Updates and rollback

- Pushing to `main` triggers CI (typecheck + build) and, if enabled, a Render
  deploy.
- Migrations are forward-only. Write a new migration; never edit an applied file.
- To roll back code, redeploy the previous Render deploy. Restoring a database
  backup is a separate, destructive operation that requires explicit approval.

## Other Node hosts

Any host that runs a Node 22 process works:

1. Build with `npm ci --include=dev && npm run build` and `API_URL` pointing to
   the internal API address.
2. Start with `node scripts/start-all.js`.
3. Expose the service's `PORT`; keep the API port private.
4. Set the same environment variables as above, including `APP_ORIGIN` pointing
   to the public HTTPS origin.
5. Apply migrations before starting the new version.

## Security checklist

- HTTPS only, with `APP_ORIGIN` set to the exact public origin.
- Strong unique `SESSION_SECRET`; rotate only with a planned session reset.
- Database TLS enabled; credentials stored as platform secrets.
- Email sender domain verified with SPF/DKIM at the provider.
- No `.env`, dumps or credentials in git.
